# Переход на свою базу — порядок действий

Пошаговый список на вечер. Каждый шаг проверяемый, откат — одна строка.

Пока в `.env` нет строки `DB_MODE=local`, всё работает через Supabase, как раньше:
новый код лежит выключенным и ничего не меняет.

---

## Почему переносим

Supabase отвечает примерно **1 секунду на запрос**, причём сам он работает 44 мс —
остальное дорога. Чтение мы спрятали за памятью сервера, а **запись спрятать нельзя**:
поэтому сохранение накладной из 30 позиций тянется секунды. Своя база на этом же
сервере отвечает за **1–3 мс**.

## Шаг 1. Поставить PostgreSQL (≈3 минуты)

```bash
apt update && apt install -y postgresql
```

```bash
sudo -u postgres createuser --pwprompt sklad
```

```bash
sudo -u postgres createdb --owner=sklad sklad
```

Проверка, что база видна только своим (должно быть `127.0.0.1:5432`):

```bash
ss -lntp | grep 5432
```

## Шаг 2. Прописать доступ в `.env` (пока без переключения)

```
PGHOST=127.0.0.1
PGPORT=5432
PGDATABASE=sklad
PGUSER=sklad
PGPASSWORD=<пароль из шага 1>
```

Строку `DB_MODE` пока НЕ добавляем — склад продолжает работать на Supabase.

## Шаг 3. Поставить драйвер базы

Выкладка делает это сама (`npm install --omit=dev` в /root/deploy.sh), но если
переносим до выкладки — руками:

```bash
cd /var/www/skladanvarov && npm install
```

## Шаг 4. Перенести данные и сверить

```bash
cd /var/www/skladanvarov && node _tools/migrate-to-local.mjs
```

Скрипт сам создаёт таблицы из `db/local-schema.sql`, переносит данные порциями
и в конце **сверяет количество строк в каждой таблице**. Supabase при этом только
читается — там ничего не меняется.

**Если хоть одна цифра разошлась — дальше не идём.**

## Шаг 5. Переключить склад

Добавить в `.env`:

```
DB_MODE=local
```

и перезапустить:

```bash
pm2 restart sklad-api && pm2 logs sklad-api --lines 20 --nostream
```

В журнале должно появиться: `[GM] База: СВОЯ (PostgreSQL здесь же), товаров в ней: 941`.

## Шаг 6. Проверка вместе с владельцем

- [ ] склад открывается, товары на месте;
- [ ] открыть товар, сохранить правку — сохраняется мгновенно;
- [ ] открыть накладную, изменить количество, сохранить;
- [ ] «Проверка склада» — история изменений остатков показывается;
- [ ] сайт и каталог открываются с телефона;
- [ ] заказ через бот доходит;
- [ ] отчёт за день приходит в бот;
- [ ] PDF и Excel выгружаются.

## Откат (если что-то не так)

Убрать `DB_MODE=local` из `.env` (или поставить `supabase`) и перезапустить:

```bash
pm2 restart sklad-api
```

Supabase всё это время остаётся нетронутым и содержит все данные.

## Шаг 7. Копии (включить сразу же)

```bash
chmod +x /var/www/skladanvarov/_tools/backup-db.sh /var/www/skladanvarov/_tools/restore-check.sh
```

Расписание (`crontab -e`):

```
7 * * * * /var/www/skladanvarov/_tools/backup-db.sh >> /var/log/sklad-backup.log 2>&1
17 3 * * * /var/www/skladanvarov/_tools/backup-db.sh --telegram >> /var/log/sklad-backup.log 2>&1
27 4 * * 1 /var/www/skladanvarov/_tools/restore-check.sh >> /var/log/sklad-backup.log 2>&1
```

- каждый час — копия на сервер (хранится 48 последних);
- каждую ночь в 3:17 — копия уходит файлом владельцу в Telegram;
- каждый понедельник в 4:27 — копия разворачивается во временную базу, строки
  сверяются с рабочей, отчёт приходит в бот.

## Чего НЕ трогаем

`config.js` остаётся как есть. Адрес Supabase и публичный ключ в нём нужны
браузеру, чтобы включился «облачный» режим — в этом режиме склад ходит за
данными через наш сервер (`/api/admin/db`), а не напрямую. Уберёшь их —
склад в браузере решит, что он в демо-режиме, и начнёт хранить данные в
самом браузере.

## Что остаётся в Supabase

Фото товаров (1 500 файлов, 178 МБ) и видео — это хранилище файлов, а не база.
Их перенос скорости не добавит, поэтому делается отдельно и позже.
